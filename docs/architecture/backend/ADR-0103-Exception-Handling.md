# 1. Context

Investment OS provides REST APIs that are consumed by multiple clients including web applications, AI services, automation workflows, and future mobile applications.

As the platform grows, exceptions will originate from multiple layers:

* API layer
* Service layer
* Repository layer
* Database
* External services
* AI providers
* Infrastructure

Without a consistent exception handling strategy, API responses become inconsistent, business logic becomes cluttered with repetitive error handling, and troubleshooting becomes difficult.

A centralized exception architecture is required.

---

# 2. Problem Statement

The platform must define:

* How exceptions are represented.
* Where exceptions should be handled.
* How exceptions are translated into API responses.
* How errors are logged.
* How internal errors are protected from external consumers.
* How exception handling remains independent of business logic.

---

# 3. Decision

Investment OS adopts a **centralized exception handling architecture**.

Exceptions are propagated through the application until they are translated into standardized API responses by a global exception handling mechanism.

Business logic raises meaningful domain exceptions and does not generate HTTP responses directly.

---

# 4. Design Goals

The exception architecture should:

* provide consistent API error responses
* separate business logic from HTTP concerns
* simplify debugging
* improve observability
* prevent information leakage
* support extensibility
* minimize duplicated error handling

---

# 5. Architectural Principles

## Centralized Handling

Exceptions are processed by a global exception handler.

---

## Layer Independence

Business layers remain unaware of HTTP response generation.

---

## Meaningful Exceptions

Exceptions should represent business or technical failures clearly.

---

## Fail Fast

Errors should be detected and propagated as early as practical.

---

## Secure by Default

Internal implementation details must never be exposed to API consumers.

---

# 6. Exception Flow

```text
                HTTP Request
                      │
                      ▼
                 Middleware
                      │
                      ▼
               FastAPI Router
                      │
                      ▼
                Service Layer
                      │
                      ▼
             Repository Layer
                      │
         Exception Raised
                      │
                      ▼
      Global Exception Handler
                      │
                      ▼
      Standard Response Envelope
                      │
                      ▼
               HTTP Response
```

Exceptions propagate upward until handled by the centralized exception framework.

---

# 7. Exception Categories

The architecture recognizes several categories of exceptions.

## Validation Exceptions

Generated when request data fails validation.

Examples:

* Invalid request payload
* Missing required fields
* Invalid parameter values

---

## Business Exceptions

Represent violations of business rules.

Examples:

* Startup already exists
* Investment exceeds allocation
* Portfolio not found

---

## Authorization Exceptions

Generated when access is denied.

Examples:

* Authentication failure
* Permission denied
* Invalid credentials

---

## Infrastructure Exceptions

Generated by infrastructure components.

Examples:

* Database unavailable
* Storage failure
* Network timeout
* External API unavailable

---

## Unexpected Exceptions

Unexpected runtime failures.

Examples:

* Programming defects
* Unhandled edge cases
* Third-party library failures

Unexpected exceptions should return generic error responses while preserving detailed internal logs.

---

# 8. Layer Responsibilities

## API Layer

* Validate requests.
* Allow exceptions to propagate.
* Avoid repetitive try/catch blocks.

---

## Service Layer

* Raise business exceptions.
* Do not generate HTTP responses.
* Do not suppress unexpected exceptions.

---

## Repository Layer

* Raise persistence-related exceptions.
* Avoid business-specific error translation.

---

## Global Exception Handler

Responsible for:

* logging
* exception translation
* HTTP status selection
* response generation

---

# 9. Logging Strategy

All exceptions should be logged centrally.

Logging should include:

* correlation ID
* request identifier
* exception type
* request path
* execution context
* stack trace (internal only)

Business validation failures may be logged at a lower severity than unexpected system failures.

---

# 10. Security Considerations

Exception responses must not expose:

* SQL statements
* stack traces
* file paths
* environment variables
* internal implementation details
* third-party credentials

Sensitive information should remain in internal logs only.

---

# 11. Integration with Response Envelope

Exception responses shall follow the standard response structure defined in ADR-0104.

Clients should receive consistent error formats regardless of where failures occur.

---

# 12. Integration with Middleware

Middleware may:

* log request context
* attach correlation identifiers
* propagate exceptions

Middleware should not implement business-specific exception handling.

---

# 13. Alternatives Considered

## Option A – Local Exception Handling

Each API endpoint handles its own exceptions.

### Advantages

* Simple for very small applications.

### Disadvantages

* Code duplication.
* Inconsistent responses.
* Difficult maintenance.

**Decision:** Rejected.

---

## Option B – Centralized Exception Framework

Exceptions propagate to a common handler.

### Advantages

* Consistent API responses.
* Reduced duplication.
* Better observability.
* Easier maintenance.

**Decision:** Accepted.

---

# 14. Consequences

## Positive

* Consistent error responses.
* Cleaner business logic.
* Improved maintainability.
* Better logging.
* Simplified testing.
* Improved client experience.

## Negative

* Requires well-defined exception hierarchy.
* Global handlers become architecturally significant.

These trade-offs are acceptable for a production-grade platform.

---

# 15. Compliance Rules

Application code shall:

* raise meaningful exceptions
* avoid generic `Exception` where specific exceptions exist
* avoid suppressing unexpected failures
* avoid returning HTTP responses from business services
* avoid exposing internal implementation details
* support centralized logging

---

# 16. Future Enhancements

Future enhancements may include:

* standardized application error codes
* localized error messages
* distributed tracing integration
* external monitoring integration
* retry classification
* circuit breaker support
* structured diagnostic metadata

These enhancements should remain compatible with the centralized exception architecture.

---

# 17. Review Schedule

Review this ADR when:

* introducing distributed services
* adding new communication protocols
* introducing event-driven processing
* adopting multi-tenancy
* modifying API error contracts

---

# 18. Decision Summary

Investment OS adopts a centralized exception handling architecture in which exceptions are raised by application components, propagated through the request pipeline, and translated into standardized API responses by a global exception handler.

This approach separates business logic from HTTP concerns, improves observability, ensures consistent client behavior, and protects internal implementation details while providing a scalable foundation for future platform growth.

**Decision:** Accepted

**Effective Release:** Phase 2 – API Infrastructure
