# Database Migration Conventions

**Project:** Investment OS
**Version:** 1.0
**Status:** Active Standard

---

# Purpose

This document defines the database migration standards for Investment OS.

All Alembic migrations **must** follow these conventions to ensure:

* Consistent migration history
* Readable revision identifiers
* Predictable upgrade and downgrade paths
* Easier code reviews
* Easier production deployments

---

# Directory Layout

All migrations are stored under:

```text
backend/
└── alembic/
    └── versions/
```

Migration files are maintained in a **flat directory**.

Example:

```text
alembic/
└── versions/
    p1_1_001_initial_schema.py
    p1_2_001_create_startup_tables.py
    p2_1_001_api_foundation.py
    p2_2a_001_password_security.py
    p2_2b_001_jwt_infrastructure.py
    p2_2c_001_create_users_table.py
```

Nested directories are intentionally avoided to remain compatible with standard Alembic tooling.

---

# Revision Naming

Investment OS does **not** use random hexadecimal revision identifiers.

Instead, revisions follow the project roadmap.

Format:

```text
p<phase>_<sprint>_<sequence>
```

Examples:

| Revision  | Description        |
| --------- | ------------------ |
| p1_1_001  | Initial database   |
| p1_2_001  | Startup tables     |
| p2_1_001  | API Foundation     |
| p2_2a_001 | Password Security  |
| p2_2b_001 | JWT Infrastructure |
| p2_2c_001 | Authentication     |
| p2_2d_001 | Authorization      |

Revision identifiers must be unique.

---

# Migration Filename

Format:

```text
<revision>_<description>.py
```

Examples:

```text
p2_2c_001_create_users_table.py

p2_2c_002_create_user_sessions.py

p2_2d_001_create_roles_table.py

p2_2d_002_create_permissions_table.py
```

Use lowercase with underscores.

Use singular nouns where appropriate.

---

# Alembic Metadata

Every migration shall define:

```python
revision = "p2_2c_001"

down_revision = "p2_2b_001"

branch_labels = None

depends_on = None
```

`down_revision` must always reference the immediate predecessor migration.

---

# Migration Structure

Every migration shall contain:

```python
upgrade()

downgrade()
```

Each function must contain a short docstring.

Example:

```python
def upgrade() -> None:
    """Create users table."""


def downgrade() -> None:
    """Drop users table."""
```

---

# Database Naming Conventions

## Tables

Plural nouns.

Examples:

```text
users

startups

founders

documents

investments

opportunities
```

---

## Primary Keys

Every table uses UUID primary keys.

Column name:

```text
id
```

Models shall inherit from:

```python
UUIDMixin
```

---

## Foreign Keys

Format:

```text
<parent>_id
```

Examples:

```text
startup_id

founder_id

user_id

investment_id
```

---

## Indexes

Format:

```text
ix_<table>_<column>
```

Examples:

```text
ix_users_email

ix_startups_name

ix_documents_type
```

---

## Unique Constraints

Format:

```text
uq_<table>_<column>
```

Examples:

```text
uq_users_email

uq_startups_name
```

---

## Foreign Keys

Format:

```text
fk_<child>_<parent>
```

Example:

```text
fk_documents_startups

fk_investments_users
```

---

# Defaults

Prefer ORM-managed defaults whenever possible.

Examples:

* UUID generation
* created_at
* updated_at

Database defaults may be used when:

* Boolean flags
* Immutable constants
* Database-managed timestamps

---

# Data Migrations

Schema migrations should only modify database structure.

Avoid:

* inserting application users
* loading seed data
* importing production data

Use separate scripts for:

```text
scripts/create_admin.py

scripts/load_seed_data.py
```

---

# Upgrade Safety

Every migration must be:

* deterministic
* repeatable
* transactional where supported
* reversible

Avoid:

* destructive updates without downgrade
* dropping columns without review
* irreversible data loss

---

# Downgrade Policy

Every migration must implement:

```python
downgrade()
```

The downgrade should reverse all schema changes introduced by the upgrade.

---

# Autogenerated Migrations

Alembic autogeneration may be used as a starting point.

Every autogenerated migration must be manually reviewed before commit.

Review:

* naming
* indexes
* constraints
* nullable settings
* default values
* foreign keys

Never commit autogenerated migrations without review.

---

# Code Review Checklist

Before merging a migration verify:

* Revision ID follows project convention
* Filename matches revision
* Upgrade succeeds
* Downgrade succeeds
* Constraint names follow convention
* Index names follow convention
* No unnecessary schema changes
* No application data inserted
* Migration reviewed manually
